# 07 — HP t730 Memory Upgrade and Post-Change Verification

**Date:** October 26, 2026 (local)  
**Platform:** HP t730 thin client running Proxmox VE 9.2.21  
**Change:** Replace two existing 4 GB SO-DIMMs with two 8 GB DDR3L SO-DIMMs  
**Outcome:** 16 GB recognized; built-in memory quick check passed; both existing VMs and key firewall functions operational.

## Change purpose

The lab originally had 8 GB RAM. With OPNsense VM 100 and Debian VM 101 running, memory headroom was limited and swap had been used. This upgrade expands capacity ahead of evaluating a future Frigate NVR proof of concept.

**Scope:** Physical memory replacement only. No changes to the production household router, network topology, VM disks, or firewall policies were required.

## Hardware procedure

1. Confirmed current VM backups existed. Shut down Debian and OPNsense gracefully, then shut down the Proxmox host.
2. Disconnected external power, observed electrostatic discharge precautions, opened the thin-client chassis, and exposed the dual SO-DIMM sockets.
3. Released both memory retaining clips, removed the original two modules, and installed the two new 8 GB modules, beginning with the harder-to-access slot.
4. Aligned the keyed notches and confirmed that each module lay flat with its retaining clips engaged.
5. Reassembled the system and powered it on.
6. The first boot displayed HP **164 — Memory Size Error**, explaining that the detected memory size had changed. BIOS reported **16,384 MB**, consistent with the new 16 GB capacity. Continued startup to Proxmox successfully.
7. Ran **HP PC Hardware Diagnostics UEFI → Memory Quick Check**, which reported **PASSED**. No extended-test option was offered in that installed diagnostic interface.

## Memory baseline and post-upgrade measurements

Measurements were taken on the **Proxmox host** with both existing VMs running (not individual guest memory use).

| Measurement | Before: 8 GB installed | After: 16 GB installed |
|---|---:|---:|
| Linux-reported total memory (`free -h`) | 6.7 GiB | 14 GiB |
| Used memory | 5.4 GiB | 5.6 GiB |
| Available memory | 1.3 GiB | 9.0 GiB |
| Swap used | 698 MiB | 0 B |
| VM count running | 2 | 2 |

**Observed improvement:** Host available RAM increased by approximately **7.7 GiB**, while reported swap usage fell to zero. Linux memory totals may be below physical installed capacity because of hardware reservation, integrated graphics, and GiB/GB differences.

### Existing VM allocations (unchanged)

| VM | Allocated memory | vCPU |
|---|---:|---:|
| 100 — OPNsense firewall | 3 GiB | 2 |
| 101 — Debian lab client | 2 GiB | 1 |

The upgrade increased **host headroom**, not the assigned memory of these VMs.

## Post-change functional and security validation

### Operating-system and guest checks

- Proxmox VE booted to the normal host login and management web UI.
- Both OPNsense and Debian VMs started and remained running.
- Debian reached its OPNsense LAN gateway: **3/3 ICMP replies, 0% loss**.
- Debian reached an external Internet test address: **3/3 ICMP replies, 0% loss**.
- The OPNsense Web GUI was accessible and the `labadmin` account successfully logged in with configured TOTP MFA.

### Firewall isolation verification

The Debian client sent three ICMP requests to the household upstream gateway: **0/3 replies (100% loss)**.

Importantly, the corresponding OPNsense Firewall **Live View** showed entries with the following **sanitized** characteristics:

| Log field | Recorded observation |
|---|---|
| Ingress interface | LAN |
| Protocol | ICMP |
| Source | Lab Debian client |
| Destination | Protected household gateway |
| Action | **block** |
| Rule label | **Block lab access to home networks** |

This verifies an actual matched firewall **block** decision rather than inferring the control from ping failure alone. Separate WAN-side blocked UDP entries in the same screen were unrelated to this LAN isolation test.

**Overall outcome:** Lab-to-home isolation continued to be enforced after the memory upgrade, while allowed access to the lab gateway and Internet remained available. These tests verify the observed destinations and protocols, not every possible private destination or application.

## Remaining considerations

- **Memory stability:** HP's quick check passed, but a full-length MemTest86+ / sustained memory test was not conducted. Optional follow-up for a long-running host.
- **Backups:** Independent VM restore testing remains deferred; archive integrity had been previously checked with matching SHA-256 hashes.
- **Frigate:** Not installed. The additional RAM improves feasibility, but camera decoding, GPU access to a prospective guest, AI detection acceleration, and recording storage are separate design decisions.
- **Storage:** The internal SSD is still small for continuous camera recording; monitor disk use and thin-pool utilization.
- **Publication safety:** Raw hardware/browser screenshots were not uploaded. Real login names, IP addresses, unique IDs, authenticator seeds, and session material should be removed before any visual evidence is published.
